# 燕云十六声服务器状态

玩家自建的非官方状态页，用来看《燕云十六声》的登录服务器现在能不能连上，还有近 30 天的可用情况和停服、异常记录。

页面：<https://yysls-status.netlify.app>

## 怎么判断的

每 3 分钟读一次官方服务器列表（游戏登录前读的就是这份），对列表里每台登录服务器做一次 TCP 握手。失败的补测一次，两次都失败才算连不上。

官方服务器列表有 A、B 两份，是两批不同的机器，换版本时玩家整批从一份切到另一份，旧的那批随后关掉。客户端用哪份由它检查更新时读的版本信息决定，这里读同一份版本信息，跟着客户端测同一批服务器。换服时记一笔：几点切到新的一批，旧的那批几点全部关闭（换服后顺带测旧的那批，最多跟 3 小时）。换服不算异常，不影响状态和可用率。

| 状态 | 条件 |
|---|---|
| 正常 | 90% 以上的服务器能连上 |
| 不停服维护 | 90% 以上的服务器能连上，同时官方公告说正在不停服维护：能登录，但部分功能用不了 |
| 部分异常 | 能连上的不到 90%，但至少有一台 |
| 停服维护 | 部分异常或一台都连不上，同时官方提前发了停服维护公告，正好在公告说的停服时间里 |
| 异常 | 一台都连不上，没有停服维护公告；临时、紧急停服也算这一种 |
| 检测失败 | 没拉到官方服务器列表，这次不算数 |

一次或连续几次检测不正常，算作一次事件，开始时间取第一次测到异常的时间。

停服公告读的是游戏登录界面的公告列表，每 3 分钟跟着检测一起读。标题带「停服」的才算停服公告，「不停服维护」「在线修复」这类维护期间照常能登录，不算。停服公告分两种：标题带「临时」「紧急」的是出了故障才决定停服，照样算停服，页面上附上公告标题；其余的是提前排好的停服维护。公告写的停服开始前半小时起就算数；写了结束时间的到结束为止，没写的从开始算一天。一次事件只要挂上了停服维护公告，就一直算停服维护，直到服务器恢复。停服维护期间登录不了，所以和停服一样计入不可用，只是颜色和标签不同。

不停服维护写在版本更新公告的正文里（标题不提），也一样每 3 分钟读一次。服务器在不停服维护开始时没有任何变化，所以开始时间就按公告写的算；维护结束时官方会开放新一批服务器、让玩家换过去（见上面的换服），所以结束时间取测到换服的那次检测，通常比官方发「维护完成」公告早。公告写的结束时间过了还没换服，就一直算维护中，过了 12 小时还没换就不再算。不停服维护期间照常能登录，计入可用，只在颜色和记录里标出来。

这里只检测能不能连上登录服务器，能连上不代表所有玩法都正常，一切以官方公告为准。

## 目录

| 路径 | 是什么 |
|---|---|
| `src/logic.js` | 判定规则、按天统计、事件合并 |
| `src/notice.js` | 从游戏内公告里挑出停服公告，读出停服时间 |
| `src/worker.js` | Cloudflare Worker：定时探测（分组交给 `Prober` 入口去测）、读游戏内公告，`/status.json` 给页面数据 |
| `test/` | 判定规则和公告解析的自检 |
| `wrangler.toml` | Worker 的配置：定时、KV 存储 |
| `site/` | 静态页，部署在 Netlify |

## 数据怎么到页面

Cloudflare Worker 每 3 分钟跑一次探测，结果累积在 Workers KV 里，访问 `/status.json` 就能拿到页面要的数据。页面部署在 Netlify，请求 `/data/status.json` 时由 Netlify 反向代理到 Worker，国内访客不用直连 workers.dev。页面只需要部署一次，数据更新了也不用重新部署。

## 公开接口

其他网站、wiki、机器人可以直接读页面用的同一份数据，浏览器里跨域请求也行：

```
GET https://yysls-status.netlify.app/data/status.json
```

- 数据每 3 分钟更新一次。响应头 `Cache-Control` 里的 `max-age` 是离下一轮结果出来还有几秒，按它定下次什么时候请求就行，提前请求拿到的也是同一份数据。
- 请用上面这个地址。`workers.dev` 那个源地址在国内基本打不开，也没有缓存。
- 表里列出的字段会保持不变；没列出的字段只给本站页面用，随时可能调整。

| 字段 | 含义 |
|---|---|
| `status` | 最近一次检测的结果：`up` 正常、`limited` 不停服维护、`partial` 部分异常、`maintenance` 停服维护、`down` 异常、`unknown` 检测失败 |
| `checked_at` | 最近一次检测的时间，Unix 秒 |
| `ok` / `total` | 能连上的服务器数 / 列表里的服务器总数 |
| `first_check` | 本站开始检测的时间，Unix 秒 |
| `notices[]` | 游戏内公告里还没过期的停服和不停服维护公告，可能还没开始：`title` 公告标题，`online` 为 `true` 是不停服维护（没有这个字段就是停服），`planned` 为 `true` 是提前排好的维护、`false` 是临时或紧急停服，`start`、`end` 为公告写的停服起止时间（Unix 秒），没写结束时间的 `end` 为 `null` |
| `days[]` | 近 30 天，从早到晚：`date` 北京时间日期，`up` 当天正常的检测占比（0～1，没数据为 `null`），`worst` 当天最差的状态，从好到坏依次是 `up`、`limited`、`partial`、`maintenance`、`down`。`limited` 计入可用 |
| `incidents[]` | 最近的停服和异常事件，新的在前：`start`、`end` 为 Unix 秒，`end` 为 `null` 表示还没恢复，`worst` 是期间最差的状态，`notice` 是这次事件对应的官方停服公告（格式同 `notices[]`），没有为 `null`。`notice.planned` 为 `true` 的事件就是停服维护，`notice.online` 为 `true` 的是不停服维护，这种事件的 `start` 是公告写的开始时间。`start` 等于 `first_check` 时，说明本站开始检测前就已经停了，真实开始时间未知 |
| `switches[]` | 最近的换服，新的在前：`start` 测到切换到新一批服务器的时间，`end` 测到旧的那批全部关闭的时间，`null` 表示还没关完；`from`、`to` 是切换前后的列表（`a` / `b`）；`unclosed` 为 `true` 表示跟了 3 小时旧的还没关完，`end` 只是不再跟踪的时间 |

## 常用命令

```bash
npm test                                               # 跑判定规则和公告解析的自检
npx wrangler@4 deploy                                  # 部署 Worker
npx wrangler@4 tail                                    # 看 Worker 的实时日志
npx netlify-cli deploy --prod --no-build --dir site    # 部署页面
```
